# Employee Project settings

An owner opens an employee's details → Advanced → Project. The page shows the employee's actual device, the existing registered projects and the current binding. Selecting another project or None requires an explicit Connect / Disconnect action. It uses the existing owner API and native Codex project permissions; it adds no execution, synchronization or deployment service.

Add project accepts a name and the canonical path of an existing Git checkout on that device. A Mac connected to its own local Home/node also offers the standard folder chooser, which resolves the chosen URL before displaying it. A phone or remote Home uses an explicit remote path. No source files are uploaded. The page explains that checkout access applies to owner-private requests and requires Codex; shared groups and scheduled work remain excluded by the backend.

In this release, send source-editing requests in the connected employee's own private chat as the owner. A project turn disables native multi-agent delegation so its checkout lease, command receipts and final Git readback belong to one verified run. The main assistant can still delegate ordinary specialty work, but that delegation does not open the helper employee's separately registered project. Connecting a project does not provide automatic project routing from the main chat. Keep main unbound for normal shared and scheduled work. Native [subagents inherit the parent sandbox](https://learn.chatgpt.com/docs/agent-configuration/subagents#approvals-and-sandbox-controls); adding a checkout path to a role's instructions would not establish a separate permission or writer lease.

Every catalog read, registration and binding captures the connection ID, canonical Home ID, device ID and actual employee ID. Both API paths carry the captured `deviceId`. Current identity, permission and reachability are checked before a write and again after each response. Folder selection also retains the identity from when the chooser opened. A changed Home, moved/deleted employee or owner revocation clears the old state. The main assistant deliberately has no Project row in this slice: its alias needs to resolve to the actual `mainAgentId` before the UI can safely offer that binding.

`GET /v1/settings/projects` supplies the revision, registered IDs and bindings. `POST /v1/settings/projects` confirms a registration; only its returned revision and project ID are used for `POST /v1/profiles/<actual-id>/project`. The model accepts a binding only when the receipt confirms the exact employee, project and newer revision. A registration followed by a network/409 binding failure is shown as registered with binding unconfirmed. Any uncertain write requires an explicit reload of current state and is never automatically repeated. An owner denial also clears the partial registration display. Existing selections cause no write.

Prepared regression coverage includes explicit device/path encoding, confirmed connection/disconnection, no-op suppression, malformed binding receipts, two-stage registration, uncertain binding readback, target change between writes, owner refusal, disabled projects and stale catalog reads. HTTP fixture coverage distinguishes GET 404 (old Home), POST 404 (missing resource) and 403 (owner-only). The existing isolated one-chat UI fixture owns one temporary committed Git checkout; the UI regression registers and connects it through these real APIs, reads back the exact employee binding/path, and confirms that no chat turn or message was sent. Fixture shutdown removes that checkout together with its own temporary Home.

Swift syntax parsing, strict fixture TypeScript checking, XcodeGen and localization checks are preparation gates. Native compilation, the Mac tests and the integrated iOS UI regression remain required before release. This slice adds no build/version bump, live project registration, deployed change or native build at preparation time.
