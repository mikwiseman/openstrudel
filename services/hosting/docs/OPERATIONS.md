# Эксплуатация WAI VDS

## Граница текущего запуска

Документированная цель этого проекта — локальный процесс на `waiMini.local`, `127.0.0.1:4781`, исходники в `/Users/mikwiseman/Documents/Codex/2026-10-04/wai-vds`, установленный runtime в `~/Library/Application Support/WAI VDS`. Для публичного экземпляра выбран существующий documented wai-pay host `root@103.45.247.25` и адрес `https://server.waiwai.is/`; новая VM для backend не требуется. У WAI VDS собственный контейнер, каталог данных и платёжная App. Развёртывание и откат описаны в `deployment/RUNBOOK.md`.

По умолчанию `WAI_PROVIDER=emulator` и `WAI_PAYMENTS=emulator`. Никакой платной инфраструктуры. Для смены режима нужна новая `WAI_DATA`, иначе приложение откажется работать, чтобы тестовые платежи и VM не смешивались с другим режимом.

Публичная версия `20261005-vds-v6` работает с открытым checkout, лимитом одной активной/зарезервированной VM и проверкой текущей публичной оценки цены. На Mac и Linux/Node 24 прошли 213/213 тестов. OpenStrudel имеет отдельные sandbox и production ключи; временный ключ пилота отозван. Текущая эксплуатация: `deployment/PRODUCTION.md`.

## Секреты и данные

`work/runtime/wai.sqlite` хранит состояния, хеши паролей, хеши сессий и зашифрованные private keys. `master.key` (32 байта, 0600) и `bootstrap-signing.pem` (0600) хранятся отдельно. Права runtime folder 0700. Временные ключи SSH тоже 0600, удаляются в finally. Обрыв питания может оставить временный файл внутри закрытого runtime directory: при восстановлении проверить только собственные `ssh-*` / `key-*`, убедившись, что процесс их не использует.

Поставщик и платежи получают secrets только из backend env. `work/kamatera.env` создан с явного разрешения пользователя из документированной панели; он содержит только два Kamatera поля. Запрещено помещать его в source archive, public directory, логи или браузер. Общий provider key видит VPN-инвентарь, поэтому каждый mutation проверяет `wai-vds-<local UUID без дефисов>`, сохранённый provider UUID и свежий provider inventory. Никаких операций со старым `wai-b2b-` или чужими VM.

В публичном запуске необходимо контролируемое TLS-окончание, Secure cookie и фиксированный `WAI_ORIGIN`. Backend принимает ровно один корректный X-Forwarded-For только от настроенного частного Docker bridge `172.18.0.0/16`, где находится Caddy. От произвольного клиента заголовок игнорируется; rate limits используют проверенный адрес. Прямой Stripe adapter поддерживает test mode; реальные карты и криптооплата идут через отдельную WAI Pay App. Прямые production Stripe keys не принимаются.

## Проверка SSH-политики

Живой образ Ubuntu 26.04.1 LTS не содержал `Include` для drop-in файлов. Одна запись в `sshd_config.d` поэтому не отключала парольный вход. `sshHardeningScript()` теперь ставит управляемый блок в начало основного `/etc/ssh/sshd_config`, проверяет `sshd -t` и эффективные значения `sshd -T`, в том числе для фактического root-соединения. Конфликтующий `Match` блокирует применение. Изменение сохраняет исходную конфигурацию, применяется атомарно и вызывает reload только при различии; ошибка reload возвращает исходный файл и повторяет reload.

На пилотной VM подтверждены `PasswordAuthentication no`, `KbdInteractiveAuthentication no` и `PermitRootLogin prohibit-password`. SSH/root продолжил работать с ключом после перезагрузки. Четыре теста с настоящим парсером sshd проверяют отсутствие Include, существующий Include, опасный Match и rollback. В production-образ WAI VDS сервер sshd не включён: он установлен только в этапе Docker для тестов.

## Диагностика и восстановление

`npm run ops -- list` выводит операции, оплаченные незавершённые заказы, ожидающие checkout и поздние оплаты `needs_refund`. Вывод без ключей и provider bodies. Стадии unknown/attention означают неопределённый результат, а не разрешение создать новую VM.

`npm run ops -- reconcile <server-id>` читает provider inventory по сохранённому имени. Это не создаёт и не удаляет VM. Сверьте также очередь Kamatera и provider billing через авторизованный аккаунт. Старые command IDs могут исчезать из очереди: отсутствие command не доказывает отсутствие VM.

`npm run ops -- tick` выполняет один проход того же durable worker. SQLite lease предотвращает одновременное создание несколькими процессами. Worker после перезапуска продолжает сохранённую стадию. Перед paid POST сохранён attempt; если процесс умер перед или после отправки, сначала выполняется reconciliation. Отсутствие VM после неизвестного POST автоматически не разрешает новый POST. Оператор должен разобраться с провайдером; это намеренная остановка, сохраняющая деньги и отсутствие дублей.

Поздний сетевой ответ не может перезаписать новое состояние операции: worker проверяет сохранённую стадию, номер попытки, версию и непросроченную lease. Сохранённый круговой курсор не даёт зависшим операциям блокировать новые заказы.

После неопределённого выключения/удаления, если состояние не подтверждается за 15 минут, операция переходит в `delete_attention`; сервер остаётся `deleting`, а worker только сверяет инвентарь. Кнопка «Проверить и продолжить удаление» разрешает свежую проверку и повтор. Неизвестное создание без найденной VM нельзя считать успешно удалённым.

При известном отказе создание допускает пользовательский «Повторить выдачу». Ошибки мощности/баланса не превращаются в потерянную оплату. Если выдача невозможна, оператор оформляет возврат в исходной платёжной системе и отмечает фактическое решение во внешнем финансовом журнале. Автоматические реальные refunds в этом MVP не реализованы.

Оплату доказывает подписанный webhook + server-to-server lookup. Если signed success пришёл раньше обновления API, вернётся 503 без consumption event ID: повтор события завершит выдачу. Если checkout истёк и это подтверждено провайдером, создаётся новая generation с новым idempotency key на том же заказе. Неизвестный checkout после 23 часов без подтверждённого истечения требует сверки, а не слепой новой сессии.

## Копии

Боевые ежедневные age-копии и проверка восстановления на Mac уже включены. См. `deployment/operations-README.md`. Закрытый age-ключ находится только на Mac в `~/Library/Application Support/WAI VDS/backup-keys/production.agekey`; хранение дополнительной пользовательской копии этого ключа необходимо для восстановления при потере Mac. На сервер передан только публичный recipient. Ниже — прежний ручной локальный способ.

```sh
node --env-file-if-exists=.env scripts/backup.mjs
```

Создаёт согласованный online SQLite backup, encryption key и signing key в timestamped `work/backups/`. Проверяет `PRAGMA integrity_check`. Это секретный backup; держите его в зашифрованном независимом хранилище оператора. Для восстановления остановить только WAI VDS, сохранить текущее состояние, восстановить три файла с 0600 в новую папку, проверить integrity, указать `WAI_DATA`, запустить и сверить все незавершённые операции.

Копия самой клиентской VM — отдельная обязанность. В текущем тарифе external provider backup выключен. UI выдаёт команду безопасной выгрузки `/srv/wai` на компьютер клиента. Она не заменяет согласованный dump базы данных и не охватывает другие папки. В production перед включением backup нужно определить включённую цену, retention, проверку восстановления и что происходит при прекращении аренды.

## Развёртывание и откат

Локальный процесс обслуживает LaunchAgent `is.wai-vds.local`. Публичный сервис — compose project/service `wai-vds` на документированном wai-pay host, данные `/srv/wai-vds/data`, релизы `/srv/wai-vds/releases`. Текущая подтверждённая версия — `20261005-vds-v6`; backup миграции — `/srv/wai-vds/backups/20261005T130609Z`, открытия checkout — `/srv/wai-vds/backups/promotion-20261005T130737Z`. Схема 7 добавляет recovery_keys и capacity_reservations; репетиция на согласованной копии подтвердила сохранение старых строк и совместимость отката. Текущую базу при откате не заменяют.

Первая установка выполняется `deployment/apply-first.sh`. Его recovery разрешён только для остановленного контейнера первого запуска без current-release; при наличии базы он проверяет schema 6, режим, integrity и отсутствие клиентских/операционных записей. База и оба ключа сохраняются до старта. Исторический code-only upgrade использует `deployment/upgrade.sh`. Переход 6→7 выполнен отдельным `production-upgrade.sh` с репетицией на копии и закрытой оплатой, затем `promote.sh open`. Для нового изменения сначала проверьте совместимость схемы. Общая последовательность:

1. Сверить живой контейнер, labels, текущий релиз и image ID. Повтор того же релиза не перезапускает сервис.
2. Проверить diff и неизменность `storage.mjs`. Изменение схемы требует отдельного плана миграции. Собрать image и выполнить все тесты в Linux, включая настоящий sshd parser.
3. Сделать online SQLite backup с `integrity_check`, копии обоих ключей, env и предыдущего compose. Текущая база продолжает принимать записи.
4. Обновить только сервис `wai-vds` командой compose с `--no-deps --no-build`. Caddy и соседние сервисы не перезапускаются.
5. Подтвердить точный новый image ID, health, публичный API, закрытый checkout и здоровье wai-pay; только затем атомарно записать current-release.
6. При ошибке вернуть предыдущий совместимый image и проверить его точную идентичность, health и закрытый checkout. **Текущую базу не заменять старым backup:** новые записи должны сохраниться. Если откат не подтверждён, явно остановиться для диагностики.

Схема v6 включает поколения оплаты, отдельные API keys, устойчивые aliases idempotency и историю WAI Pay attempts. Изменения аддитивные, но откат финансовой логики требует версии, понимающей актуальные payment attempts; восстановление старой базы поверх новых платежей без reconciliation недопустимо. База хранится только на локальном диске одного backend host; SQLite WAL не предназначен для общего NFS. Несколько процессов одного host протестированы, распределённый кластер не заявлен.

## Завершённый живой acceptance 5 октября

Пользователь разрешил одну временную VM Kamatera с лимитом $10. Пилот выполнен в отдельной базе и с локальным spend gate: публичные настройки не открывались. Профиль — Amsterdam, image `EU:7a74bdc0c8034ce9a1fd28d8ed91f8f5`, 1A/2048 MB/20 GB/t5000, одна IPv4, без backup и management. Списание с покупателя не выполнялось: использован подписанный тестовый checkout.

Подтверждены ровно одна попытка создания и сохранённый provider UUID, SSH/root со скачанным ключом, все три шаблона последовательно на этой VM, Docker, внешний HTTP, восстановление SSH/Docker/HTTP после reboot, экспорт и восстановление тестового файла. «Чистый Linux» проверял базовую SSH-настройку после других шаблонов; он не удалял Docker/nginx и не являлся отдельной свежей VM. Клиент OpenStrudel проверил status/access существующего сервера и скачал настоящий ключ; временный API-ключ затем отозван. Создание всех трёх типов через постоянный клиент проверено только в sandbox. Отзыв API-ключа закрывает API-доступ, но сам по себе не отзывает ранее скачанный SSH-ключ; пилотная VM удалена.

Удаление выполнено через off → terminate без force, отсутствие VM подтверждено. Финальный inventory содержит те же 17 прежних VM. Доказательства без credentials: `outputs/live-pilot.json`. Начальный SSH host key по-прежнему основан на TOFU с проверкой текущего IP через API; затем используется pin. Отдельная аттестация первого ключа через console не заявляется.

База цены аккаунта для профиля — $6/месяц плюс известная комиссия 2%. После удаления текущий usage-отчёт показывает $0.001810: включённое состояние $0.00144, выключенное $0.00034 и сеть $0.00003. Это не финальный invoice: налоги, комиссия и округление остаются на сверке. Строки после удаления названы Hourly, хотя активная VM показывала monthly; причина не установлена, общего правила возврата за monthly VM из этого результата не следует.

## Границы подтверждения

Checkout открыт по последующему запросу пользователя о production. Карта и USDT используют LIVE merchant; реквизиты и контакты опубликованы, резервирование, восстановление аккаунта, независимые копии и мониторинг включены. Реальные денежные зачисления и выплаты в проверке не выполнялись. Налоги и окончательный invoice Kamatera не подтверждены; публичная цена калькулятора помечена как estimate. Монитор сообщает о проблемах в systemd; внешняя отправка email/Telegram не настраивалась. Сервис работает на одном backend host, HA и отдельные backups клиентских VM не заявляются.
